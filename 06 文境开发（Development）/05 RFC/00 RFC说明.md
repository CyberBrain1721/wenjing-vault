# RFC说明

RFC（Request for Comments）是 Development 中用于管理开放设计议题的模块。

文境保留 RFC 这一国际软件工程术语，但不完全沿用其传统使用方式。

在软件工程中，RFC 用于在标准正式建立之前，公开提出设计方案并持续讨论，最终形成行业共识。

在文境中，RFC 承担的是另一项职责。

它负责保存那些尚未形成最终架构决议，但具有长期研究价值的问题。

因此，RFC 不属于正式系统。

它也不代表最终设计。

RFC 的存在，是为了避免未经充分验证的思想直接进入文境。

---

# RFC的定位

Development 采用逐步收敛（Progressive Convergence）的开发方式。

任何新的理念、机制、架构或系统能力，都不应直接进入正式文档。

它们首先进入 RFC。

经过持续讨论、第一性推导、实际验证以及多轮设计评审之后，才可能形成正式架构决议。

RFC 保存的是研究过程。

Architecture Review 保存的是最终决议。

两者职责完全不同。

---

# RFC的职责

RFC 回答的问题不是：

"最终应该怎么设计。"

RFC 回答的问题是：

"这个问题是否值得继续研究。"

因此，一个 RFC 可以持续存在很长时间。

它可以不断补充新的观察、反例、实验结果与设计假设。

在形成充分证据之前，不应进入正式系统。

---

# RFC的生命周期

每一份 RFC 均遵循统一生命周期。

提出问题。

建立 RFC。

持续研究。

形成架构评审。

进入正式系统。

思想演化记录于《境志》。

如果最终决定放弃，则关闭 RFC，并记录放弃原因。

RFC 本身不形成规范。

只有完成 Architecture Review 后，相关内容才具有正式效力。

---

# RFC应包含的内容

每份 RFC 应至少回答以下问题：

研究的问题是什么。

为什么值得研究。

目前已经确认了什么。

目前仍然存在哪些未知。

有哪些设计假设。

准备如何继续验证。

哪些条件满足后，应进入 Architecture Review。

---

# 使用原则

RFC 不追求尽快形成答案。

RFC 的职责，是延迟重要决策。

对于任何影响文境底层架构的重要设计，应优先保证研究充分，而不是快速完成。

Development 宁可保留一个长期开放的 RFC，也不应让未经验证的思想进入正式系统。

---

# 最后

RFC 保存的是未来。

Architecture Review 保存的是决定。

正式文档保存的是原则。

境志保存的是演化。

四者共同构成文境长期开发的方法体系。
