# RFC-001｜文境是否保留RFC机制

## 提出背景

随着 Development 模块逐步建立，文境开始采用软件工程方式管理系统开发。

与此同时，一个新的问题出现：

文境是否需要引入 RFC（Request for Comments）这一机制。

RFC 来源于软件工程。

而文境并不是一个传统的软件项目。

因此，需要重新判断 RFC 是否真正适合文境，而不是简单沿用软件工程中的开发习惯。

---

# 核心问题

RFC 在文境中是否具有独立价值。

如果存在，它解决了什么问题。

如果不存在，它是否会与 Architecture Review、Bug 或开发日志发生职责重叠。

---

# 当前观察

经过目前开发过程的回顾，可以确认：

Development 已经拥有以下模块：

Bug。

Architecture Review。

开发日志。

正式系统。

境志。

但在 Architecture Review 之前，仍然缺少一个用于长期研究开放问题的阶段。

近期关于 Creator Profile、成长路径、人机协作模式等讨论，都经历了不断推翻与重新建立的过程。

如果这些设计直接进入正式系统，将不断产生系统返工。

因此，Development 需要一个能够容纳长期研究，而不形成正式决策的模块。

---

# 当前假设

RFC 的价值，不在于征求评论。

RFC 的价值，在于延迟重要决策。

它允许系统长期保存尚未形成结论的问题，并持续积累观察、验证与反例。

只有当研究达到足够成熟时，才进入 Architecture Review。

因此，RFC 更接近研究阶段，而不是设计阶段。

---

# 当前未解决的问题

RFC 是否仍应保留 Request for Comments 这一名称。

未来是否需要根据文境自身的发展，建立新的开发术语。

RFC 是否需要增加实验记录或验证机制。

多个 RFC 之间是否应建立依赖关系。

这些问题目前均未形成结论。

---

# 后续计划

继续使用 RFC 机制参与文境开发。

观察未来多个 RFC 的实际使用效果。

当 RFC 的职责边界完全稳定后，再决定是否调整名称或进一步完善 Development 方法体系。
