
## 今日主题

今天的工作围绕 Inbox Standard 展开，从发现 Obsidian 兼容性问题开始，最终推动了 Convention 目录内全部 8 份开发规范的格式统一。

这看似是一次格式调整，实质上是文境开发规范从"设计文档"向"工程文档"的一次系统化转型。

# 一、Inbox Standard 的 Obsidian 兼容性修复

今天最初的问题是 Capture Workflow 输出的 Inbox 文档中，YAML frontmatter 的嵌套结构在 Obsidian Properties 面板中不可引用。

原因很明确：Inbox Standard §4 定义的 YAML 模板使用了三层嵌套对象（resource / knowledge / metadata），而 Obsidian Properties 系统只支持扁平键值对。`status` 和 `type` 可以正常显示，但 `resource.id`、`knowledge.canonical` 等嵌套字段均无法作为独立属性查询。

修复分为三步：

第一，将嵌套结构展平为前缀式扁平键值对。`resource.id` → `resource_id`，`knowledge.canonical` → `canonical`，以此类推。

第二，经过讨论后进一步精简字段。删除了 `resource_id`、`resource_source`、`canonical`、`related`、`author` 五个字段，随后又删除 `resource_type` 和 `language`。`resource_url` 改为可选——有真实 URL 时保留，为空时删除整行。

第三，新增 §6.4（后重编号为 §7.4）References 规范：明确 References 使用 Obsidian 双向链接 `[[文档标题]]` 格式，链接至 Inbox、成卷、归藏、道中的实际文档。无关联内容时留空，不得填入 Knowledge Map 节点作为替代。

Inbox Standard 的 YAML 结构最终从 15 字段精简为 10 字段，简化为 8 字段：

```
status / type / resource_url(可选) / resource_capture_time / resource_policy / tags / publish_date / confidence
```

# 二、全部 24 个 Inbox 文件 YAML 标准化

Inbox Standard 修改后，对藏阁 Inbox 目录下的全部 24 个文件进行了逐一轮查和修复。

修复包括：

- 旧格式 YAML（中文键名：状态/类型/来源/date）→ Inbox Standard 格式（英文键名）
- tags 中的 `#` 前缀 → 标准 YAML 列表格式
- 补充 `resource_capture_time`、`resource_policy`、`confidence` 等缺失字段
- 为所有文件补上 `## References` 章节（空或含双向链接）
- 清除了所有填入 Knowledge Map 节点的伪关联链接（`[[AI]]`、`[[Agent]]` 等）

经过多轮扫描和修复，最终确认 24 个文件零旧格式残留。

# 三、Markdown 原文收录规则

在处理 `【课】一堂 · 关键假设与业务验证.md` 时发现：该文件原始内容本身为 Markdown 格式（课程笔记），但此前仅以大纲摘要形式保存于 Original Content 中。

这触发了新的规则：当原始资源为 Markdown 格式时，应全文直接收录，不得以摘要或要点提取替代。该规则已写入 Inbox Standard §7.1（原 §6.1）。

文件已据此更新，Original Content 替换为附件全文，保留原始 Markdown 结构与格式。

# 四、Convention 目录格式统一

完成 Inbox Standard 的修改后，以此为标准对 Convention 目录下全部 8 份开发规范进行了格式统一。

统一的规则：

- 主节标题统一使用 `## N.` 编号格式
- 子节统一使用 `### N.N` 编号格式
- 节间以 `---` 分隔
- 同主题短句合并为段落，消除碎片化换行
- 代码块（YAML、Markdown、流程图）标准化
- 表格对齐

修订的文件清单：

| # | 文件 | 主要修复 |
|---|------|----------|
| 01 | 文境输出协议 | 混合 `##` → 统一编号，段落合并 |
| 02 | 命名规范 | `#` 标题 → `## N.` |
| 03 | Runtime State Specification | 混合 `#`/`##` → `## N.` + `### N.N` |
| 04 | Knowledge Map Convention | `#`/`##` 混杂 → `## N.`，流程代码块化 |
| 05 | Capture Convention | `#` 标题 → `## N.`，Pipeline 代码块化 |
| 06 | Resource Policy Standard | `#`/`##`/`###` 三级混用 → `## N.` + `### N.N`，推荐表化 |
| 07 | Inbox Standard | 本轮主力修改，已完成 |
| 职责说明 | 表格对齐 |

全部修改遵循「不修改原文内容，只优化格式」的原则。

# 六、今日总结

今天的开发工作呈现出一个值得记录的模式。

最初的问题是 YAML 嵌套结构在 Obsidian 中不可用。这只是一个点状的技术问题。但在修复的过程中，暴露出了一系列连锁问题：

- Inbox Standard 本身需要多轮字段精简才能达到合理规模
- 24 个已存在的 Inbox 文件处于多种不同的格式状态
- Convention 目录内 8 份文档的标题层级、编号方式、段落组织方式互不统一

如果只修复第一个问题，后面的问题会在未来的每一次操作中反复出现。今天选择了一次性系统性清理。

更值得关注的是格式统一背后的工程意义。在规范修改的过程中，一个反复出现的原则是「不修改原文内容，只优化格式」。这要求对每一份文档的修改都精确控制在结构层面，而不是借机重写内容。这与软件工程中「重构不改行为」的原则完全一致。

文境的开发规范正在从「能看懂」向「能维护」过渡。格式统一，是实现这一过渡的基础工程。
